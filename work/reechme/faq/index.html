Questions and limits

The honest FAQ.

This page answers product questions. It is not legal, medical, or clinical advice.

Is ReechMe a real safety service?

No. This is a browser-based product prototype built to test an interaction model. It does not send alerts, make calls, send SMS messages, contact trusted contacts, request live location, or dispatch emergency services. Refreshing the page clears the demo state.

If you need help now, use the verified support details or contact emergency services directly.

What happens when I activate the demo SOS?

A local event is created in the browser’s memory. If the demo is online, the event moves through simulated sync, queued delivery, sending, and delivered states. If the demo is offline, it is marked saved locally and no recipient alert appears.

Delivery is a simulation. There is no SMS gateway, push provider, or backend. “Delivered” means the demo state machine reached that state — not that a person received or read anything.

Does it use my real location?

No. The browser geolocation API is not called, and the site sends aPermissions-Policyheader denying geolocation. Any map is a schematic illustration. It is labelled as illustrative and must not be read as a live position.

The keypad channel has no location capability at all. It shows a previously saved area, clearly marked as historical, rather than inventing a GPS fix.

What does the demo PIN protect?

Very little, deliberately. The PIN is 2468 and is displayed in the demo. It is not authentication, not encryption, and not stored. Private mode demonstrates a lower-discovery entry point; it cannot hide the app from someone with access to the device.

Can a trusted contact acknowledge an alert?

In the demo, yes — but only after the simulated delivery reaches that contact. The contact view is a second fictional screen inside the same browser. Acknowledgement adds an entry to the timeline and pauses demo escalation, but the session stays open.

Acknowledgement is not proof of safety, not a dispatched responder, and not a resolution. Only the device owner ends the session in this prototype.

What happens if I go offline?

Activation while offline creates a local record only. No alert is shown to the fictional contact. When you restore the demo connection, the same event enters pending sync, then syncs and begins simulated delivery. The event ID and original activation time are preserved, so reconnection does not create a duplicate.

If you cancel while offline, the record becomes “closed before sync” and is never revived as a fresh alert. Real-world offline guarantees would depend on the operating system, app permissions, and mobile network, and are not proven by this demo.

How does the keypad-phone scenario work?

Press and hold 9 on the simulated keypad, or use the accessible one-press alternative. A fictional service call is simulated. If the demo is online, the call creates the same kind of demo event as the smartphone flow, delivered as an SMS-style alert. If the simulated call fails because the demo is offline, no event and no SMS are created.

No real number is dialled. No real service number has been allocated for ReechMe. The keypad is an original browser simulation, not an emulator of a specific phone.

Why isn’t there a live map?

Because the prototype cannot honestly provide one. Drawing a real map would require geolocation permission, a mapping provider, network requests, and a consent and privacy design that the demo does not have. Instead, the location card uses a labelled schematic area to demonstrate sharing, expiry, revocation, and stale states.

Is the prototype accessible?

It targets WCAG 2.2 AA: semantic landmarks, keyboard-operable controls, visible focus, text labels, live announcements, reduced-motion support, and no reliance on colour alone for essential meaning. The keypad hold action has a non-hold alternative.

It has not been independently audited or tested with disabled users. Automated checks and manual review cannot establish full conformance, particularly for assistive technology, cognitive load, and translation. This gap is a known limitation, not a claim of compliance.

Why does the design avoid fear and gendered marketing?

Safety products often use threat, urgency, or gendered stereotypes to drive engagement. That can increase anxiety, exclude people, and shift responsibility onto the person at risk. The prototype uses a calm teal-and-warm palette, neutral language, and no countdown pressure for the primary action.

The check-in timer is a functional exception. It is clearly accelerated in the demo and describes a missed check-in as a fact, not as evidence that harm occurred.

What data does the demo collect?

The demo stores state in React memory for the current tab. It uses no account, cookie, analytics, advertising script, localStorage, or database. There is no contact form submission. Standard web-server request logs may exist depending on where the site is hosted, but this build does not add analytics or tracking.

Do not enter real names, addresses, health information, or other sensitive details anywhere in the prototype. See the privacy page.

Were the support details verified?

The support page lists its sources and records a verification date of 22 October 2026. It uses official South African government, SAPS, Department of Justice, and SADAG pages. It does not claim 24-hour availability unless the source states it, and it does not invent response times or outcomes.

Phone numbers can change. Use the source links if a number is unreachable. The support information is separate from the demo and does not imply any partnership with those organisations.

What would come next?

Real use would require a backend with idempotent event creation, server-enforced permissions, audited delivery evidence, key management, a privacy impact assessment, abuse and threat modelling, independent accessibility testing, safeguarding protocols, and operational agreements with support services. None of that exists in this prototype.

The immediate next step is evaluation with the people the concept is meant to serve — especially keypad-phone users, disabled people, and organisations with existing safeguarding expertise.
