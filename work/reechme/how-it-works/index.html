Interaction model

One action, configured before the moment.

ReechMe is built around a single, pre-configured safety action. The interface is designed to make the state of that action legible — not to ask someone under pressure to explain, select, or justify.

The flow

Six steps, each visible.

The prototype exposes the whole path so that a demonstration does not hide the gaps between “created”, “sent” and “received”.

01

Configure once

Choose a primary and backup trusted contact, the information they may receive, and whether location is allowed. This is done before an event.

02

Open private mode

The safety action sits behind a private mode. In the prototype this is a four-digit demo PIN, not real authentication.

03

Activate once

One deliberate action creates the event. No journey, description of what happened, or recipient selection is required.

04

Watch delivery

Each recipient and channel gets its own state: not attempted, queued, sending, delivered, failed, acknowledged or stopped.

05

Receive acknowledgement

A trusted contact can acknowledge. The session stays open. Acknowledgement is not proof of safety and does not dispatch help.

06

End deliberately

The device owner can close or cancel the session. Future simulated sharing and escalation stop; the record remains.

State separation

What each status actually claims.

One reducer, four distinct kinds of state. Keeping them apart prevents the most misleading interface pattern in safety products: a single tick that implies more than the system knows.

The demo never automatically resolves an event after acknowledgement. Only the device owner ends the session. This is a deliberate product decision, not a missing feature.

Private mode

Discretion, stated honestly.

Private mode is intended to reduce casual discovery of the safety screen. It is not encryption and it does not hide the app from someone who controls the device.

The PIN is a prop

The demo PIN (2468) is displayed on the screen. It is not authentication, not stored, and not a security boundary.

No story required

The safety action does not include a journey form, a reason field, or a mandatory description. Configuration happens in advance.

What is configured in advance

Primary and backup contact

The prototype starts with two fictional contacts. The primary is notified first after a missed check-in; escalation to the backup is an explicit step.

Location permission

Optional and scoped. If it is denied, the event still proceeds. The demo uses a schematic map and never calls the browser geolocation API.

Channel and content

Smartphone alerts can include an illustrative location view. The keypad channel sends an SMS-style alert with no invented current position.

Acknowledgement permission

Contacts can acknowledge a delivered alert. The contact view cannot close the sender’s session or claim that help has arrived.

Check-ins and reconnection

Time, absence and failure need their own language.

A missed check-in is a factual state. It is not an accusation, a diagnosis, or a claim that someone has been harmed.

Accelerated check-in

A timer, not a surveillance window.

  1. Start: the demo creates a 30-second check-in. No alert is sent.
  2. Confirm: “I’m safe” closes the check-in without notifying anyone.
  3. Extend: adds 15 seconds in the demo. No alert is sent.
  4. Missed: the primary contact receives a simulated alert and optional illustrative location. The session stays open.
  5. Escalate: the backup contact can be added only by a separate explicit action, which is the maximum demo escalation level.

Offline reconciliation

No duplicate alert after reconnection.

  1. Offline: the event is saved locally. No contact alert is shown and no delivery is claimed.
  2. Reconnect: the same event enters pending sync. The original activation time and event ID are preserved.
  3. Sync: delivery begins for the existing event. No second event is created.
  4. Cancelled offline: the event becomes “closed before sync” and is never revived as a fresh alert.
  5. Limits: real offline delivery depends on device, OS, and provider behaviour. The demo cannot prove those guarantees.

Keypad channel

A service call, an SMS alert, and no invented map pin.

A keypad phone can hold 9 to reach a fictional ReechMe demo service. The connected call creates the same shared event, delivered as an SMS-style alert.

No real phone number is allocated. The service number is deliberately fictional.
If the simulated call fails offline, no event and no SMS is created. The failure is shown, not hidden.
The contact view can show a previously saved area, clearly labelled as historical. It is not a current location.

Accessibility and inclusion

Designed for more than the ideal user.

The prototype targets WCAG 2.2 AA and avoids relying on colour, precise timing, or fine motor control for essential actions.

Responsive

Mobile tabs keep the shared demo state while the layout changes.

Accessible alternatives

The keypad hold-9 action has a one-press alternative. The SOS action is a single button.

Reduced motion

Animations collapse to near-zero duration when the operating system requests reduced motion.

Status announcements

State changes are announced in a polite live region, and every control has a text label.

Accessibility is a target, not a completed certification. This prototype has not been tested with assistive technology users or audited by a third party. That gap is documented in the FAQ.
